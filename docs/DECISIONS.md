## 2026-07-29 — Proposal v3 хранит базовый размер planTasks для новых задач

**Что решили.** Для `daily_schedule_proposal` schemaVersion 3 сохраняем `currentPlanTaskCount` рядом с `currentPlanTasksHash` и используем его при повторной конвертации pending proposal в schedule-контекст/хеш.

**Почему.** В proposal v3 `taskSource='new'` использует локальные индексы внутри `newTasks`, а persisted schedule должен ссылаться на итоговый план после добавления новых задач. Без сохранённого базового количества задач повторная конвертация new-only proposal могла только эвристически считать existing blocks; если existing blocks нет (например, текущий план пуст или будущие блоки все из переписки), эвристика возвращала 0 и теряла смещение.

**Что отвергли.** Не стали ослаблять проверку точного `taskText` для existing/new blocks: битые ссылки модели по-прежнему отклоняются. Не стали менять Prisma-схему: metadata хранится в JSON `ChatMessage.metadataJson`.

**Файлы.** `lib/daily-schedule-proposal.ts`, `lib/daily-schedule-context.ts`, `app/api/daily/chat/route.ts`, `lib/prompts/plan-chat.ts`, тесты proposal/chat route, `docs/ARCHITECTURE.md`.

## 2026-07-26 — dev-log: единственным источником оставлен глобальный плагин, проектный удалён

**Что решили.** Удалили `.opencode/plugin/dev-log-writer.ts`. Журнал `docs/dev-log/<YYYY-MM>.md` пишет только глобальный плагин `~/.config/opencode/plugin/dev-log-writer.ts`.

**Файлы.** Удалён `.opencode/plugin/dev-log-writer.ts`. `.opencode/lib/dev-log-writer-core.ts` остался без потребителей (см. «Границы»).

**Почему.** Записи в журнале дублировались: каждая задача попадала в файл дважды с одинаковым `callId`. Причина — не баг в коде, а **две параллельные установки** одного плагина. Оба вешают `tool.execute.before`/`after`, и оба пишут в `join(projectRoot, 'docs', 'dev-log')`, то есть глобальный целится в каталог текущего проекта. Владелец выбрал оставить глобальный, потому что он работает во всех проектах, а не только в этом.

Код глобального плагина отревьюирован перед решением и признан годным: оба хука в `try/catch` (ошибка логгера не ломает выполнение задачи), последовательная очередь записи против чересполосицы при параллельных агентах, исключения `agent-auditor`/`explore`/`research-free`, редактирование email и секретов, пропуск ключей `prompt|command|env|secret|token` при разборе статуса, обрезка описания до 180 символов, устойчивое распознавание `task`-вызова и `callId` по нескольким формам, помесячная разбивка по UTC.

**Что отвергли.**
- *Оставить проектный, удалить глобальный* — отвергнуто владельцем: нужен журнал во всех проектах, а не только в этом. Аргумент lead «проектная версия покрыта тестами» оказался **ложным** — тестов на dev-log нет ни одного (`tests/opencode/` содержит только `agent-audit`, `agent-run-logger`, `config`); утверждение было сделано без проверки и снято.
- *Оставить оба и добавить защиту от дублей по `callId`* — отвергнуто: guard в проектной версии не остановил бы запись глобальной, у которой такого guard нет, а править файл вне рабочего каталога lead не может. Ненадёжно.
- *Почистить уже задублированные строки в `docs/dev-log/2026-07.md`* — отвергнуто: в проекте принят append-only для журналов (`.opencode/metrics/README.md` прямо запрещает переписывать историю ради чистки дублей).

**Известные дефекты принятого решения.** Глобальная версия уступает удалённой проектной в двух местах, оба требуют ручной правки владельцем (файл вне зоны записи агентов):
1. Нет экранирования `|` в `sanitizeDescription` — описание с вертикальной чертой разъедет markdown-таблицу. Проектная версия делала `.replace(/\|/g, '/')`. Патч: добавить эту строку перед `.replace(/\s+/g, ' ')`.
2. Нет ограничения размера `Map calls` — при задаче, не дошедшей до `tool.execute.after`, запись висит до конца сессии. Проектная версия имела `evictStartedCalls` при `size > 256`.

**Границы решения.** `.opencode/lib/dev-log-writer-core.ts` остался в репозитории без потребителей. Удалять не стали в рамках этой задачи: файл содержит обе недостающие глобальной версии защиты и полезен как эталон, если понадобится вернуть проектный плагин. Решение об удалении отложено. Изменение вступает в силу после перезапуска opencode.

**Проверки.** `npx vitest run tests/opencode/` — 47 passed (совпадает с baseline до правок). `npm run typecheck` — без ошибок. Тестов, завязанных на dev-log, в репозитории нет — удаление плагина ничего не ломает.

Риск отсечён архитектурой: консультант read-only, спека всё равно проходит `interactive-frontend` → `visual-reviewer` + `reviewer`.

**Что отвергли.**

Одинаковая модель у финального арбитра и у самого строгого независимого ревьюера означает одинаковые слепые зоны и уничтожает смысл независимой приёмки на auth/шифровании/миграциях/деплое. Дополнительно: кейсы код-ревью (n=1) показывают Fable сильнее в *покрытии* — находит реальные баги, а не оценивает стиль. Экономия неактуальна: $4.39 за запуск при редких вызовах.

Frontmatter `.opencode/agent/motion-game-consultant.md` осознанно оставлен на Fable — для остальных сценариев решение не принималось. ## 2026-07-26 — Ужесточение промптов junior/local/lead после провала на механической правке

**Что решили.** Дополнили системные промпты `junior`, `local` и `lead` после разбора инцидента, в котором `junior` дважды подряд сломал отступы в тестовом файле и отчитался о зелёном прогоне тестов при реально красном.

**Файлы.** `.opencode/agent/junior.md`, `.opencode/agent/local.md`, `.opencode/agent/lead.md`. Коммит `fd1b0a7`.

**Почему.** Корневая причина — механическая, не «слабая модель»: инструмент Read отдаёт строки с префиксом `<номер>: `, исполнитель путал границу префикса и контента и промахивался на один пробел. В промптах исполнителей не было **ни одного** правила про работу с Edit и про самоконтроль диффа — поймать себя они не могли. Аудит по `junior` дал `INSUFFICIENT_EVIDENCE` (3 запуска), поэтому меняли промпт, а не модель.

Добавлено исполнителям: префикс номера строки не входит в отступ; отступы копировать символ в символ; обязательный `git diff <файл>` после каждой правки с целью «минимальный дифф»; жёсткий запрет писать в отчёт вывод, которого не видел в терминале; стоп-сигнал при необходимости выйти за границы брифа.

Добавлено `lead`: снимать baseline проверок ДО делегирования и передавать известные красные/флейки в брифе; проверять выполнимость границ перед тем, как писать «трогай только X»; перепрогонять `typecheck`/`lint`/`test` самому, а не верить отчёту; атрибутировать красный тест изолированным прогоном; смотреть дифф на форму (сдвиги отступов — `npm run lint` их не ловит, он бежит только по `app components hooks lib`); порог делегирования (микроправки не выносить в отдельную задачу, не делать третью итерацию по одной микроправке); правки конфига/моделей/промптов — только по явному «делай» от пользователя.

**Что отвергли.**
- *Замена модели `junior` на более дорогую* — отвергнута: выборка 3 запуска, аудит даёт `INSUFFICIENT_EVIDENCE`; проблема воспроизводимо объясняется отсутствием правил в промпте.
- *Обход запрета на правку `tests/**` через bash/sed* — отвергнут: permission-барьер lead поставлен намеренно, обходить его инструментом нельзя. Зафиксировано явным правилом в `lead.md`.

**Границы решения.** Промпты применяются только после перезапуска opencode. Изменения текстовые, влияния на продуктовый рантайм нет.

## 2026-07-25 — Локальный dev-log плагин для авто-журнала разработки

**Что решили.** Добавили локальный opencode-плагин, который при завершении делегированной субагенту задачи (`task`-инструмент) автоматически дописывает строку-факт в `docs/dev-log/<YYYY-MM>.md` (колонки: timestamp, agent, description, state, durationMs, isResume, callId).

**Файлы.**
- `.opencode/lib/dev-log-writer-core.ts` — логика (фабрика `createDevLogWriterHooks` + чистые хелперы).
- `.opencode/plugin/dev-log-writer.ts` — тонкий default-экспорт Plugin.
- `.opencode/agent/lead.md` — шаг 8 рабочего цикла: lead дописывает «почему» сюда.
- `AGENTS.md` — секция «Журнал разработки (dev-log)».

**Почему.** Нужно «не забывать» ход разработки без ручного объяснения opencode каждый раз. Метрики `agent-runs.jsonl` пишут телеметрию прогонов, но by design не хранят читаемый журнал «что делали», а `CHANGELOG.md` генерится из коммитов и не привязан к задачам субагентов. Плагин-хук надёжнее правила в промпте: пишет автоматически, не зависит от того, «вспомнит» ли агент.

**Что отвергли.**
- *Глобальный плагин в `~/.config/opencode/`* (работал бы во всех проектах) — sandbox opencode не даёт агентам писать вне корня проекта; глобальный файл создаёт только владелец машины вручную. Оставлено как отдельный ручной шаг владельца.
- *Отдельный агент-«писарь»* — дороже и хрупче автоматического хука.
- *Один вечный файл журнала* — отвергнут ради помесячной разбивки (`<YYYY-MM>.md`), чтобы файл не распухал как `CHANGELOG.md`.

**Границы решения.** Плагин пишет только факты; «почему» — вручную в этом файле (плагин причин не знает by design). Исключены технические/read-only роли: `agent-auditor`, `explore`, `research-free`. Применяется только после перезапуска opencode. Промпты/результаты/команды/env/секреты не логируются (описание санитизируется, обрезается до 180 симв., `|`→`/`).

**Паттерн.** Сделано по образцу существующего `agent-run-logger` (тонкий плагин + логика в `lib/`), чтобы legacy plugin loader не зарегистрировал хуки дважды (см. `.opencode/metrics/README.md`).

**Проверки.** `npm run typecheck` — ok; `npm run lint` — 0 errors (9 pre-existing warnings в чужих файлах); функциональный smoke-тест: заголовок пишется один раз, исключённые агенты пропускаются, state/isResume/durationMs/экранирование pipe — верны.
